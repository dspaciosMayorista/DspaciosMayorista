## 4. Business questions (one batch, with recommendation)

**#98 signature**
- **Q1 Mechanism.** Options: (a) signature image + explicit electronic acceptance of a frozen version (recommended), (b) cryptographic digital signature/certificate. Recommendation (a): ally uploads PNG/JPG once, and must press "Accept version N" per cuenta de cobro; each acceptance stores actor, timestamp, document hash and signature-image hash; the document says it is an electronic acceptance, not a digital certificate. Example: Laura (freelance) accepts cuenta de cobro of contract 00-0451, $1.250.000 net commission, version 1.
- **Q2 Who signs.** Page already blocks agencies (they invoice electronically). Confirm: freelance only?
- **Q3 After a change.** If staff change retention/% after acceptance, recommendation: keep the signed version immutable and visible, generate a new version that needs a new acceptance, never overwrite. May staff void a signed version (reason required)? Is a stored signature reusable across documents (recommended, with per-version click) or captured each time? Are name/bank data frozen in the snapshot (recommended)?

**#35/#31** — **Q4 "PVP seal".** Today a comparison document shows the parent "a PVP" and the child has a `cotizacion_neto` row with modalidad pvp. Do you want a visible stamp/label on the document, or only the stored seal? Should B2B-without-ally PVP (Q-5 "legada") remain possible for **new** rows? Recommendation: stored seal only (no new label), and no new B2B row without a verified ally.

**#32** — **Q5 Branding.** Logo replaces or co-brands with D'spacios? Who is the legal issuer line (recommendation: unchanged, the agency in `agencias`; the ally logo is presentation only)? Shared client links `/cot/<token>` are public to anyone with the token, so the logo must be readable by the token holder: recommendation private bucket served through the quotation token, PNG/JPG/SVG-rejected, ≤ 1 MB, no-logo fallback shows only the agency identity.

**#25** — **Q6.** Which ally edits need staff approval (recommendation: none new; keep immediate edits with audit) and may staff edit nombre/telefono/email/NIT (recommendation: yes, audited)? Should the ally see their own change history (recommendation: staff-visible per-ally history only for now)?

**#84** — **Q7.** Once a quotation becomes a contract, is the portal figure the frozen quotation total or live `ventas.precio_venta` (recommendation: contract live value, quotation total kept as labelled history)? Show "updated by D'spacios" marker? (recommendation: no).

**#48** — **Q8.** NETO in the normal manual quotation: same roles as #50 (superadmin/gerencia/administracion/operaciones; `venta` only own)? Same margin rule (≥6 %, 2 % tickets-only with superadmin authorization)? Confirm NETO is the amount due and no second commission applies (as in #97).

**#62** — **Q9.** Recovery by emailed link (recommended, native) or by code? Should unverified email block login or only B2B approval? Existing users were created pre-confirmed: leave as verified (recommended). Code validity window (recommendation 15 minutes, resend allowed with cooldown).

**#76/#77** — **Q10.** Who owns an ally's end client (ally or D'spacios)? May other allies or staff see them? Consent wording for ally-supplied personal data. Until answered, no implementation.

**#78** — **Q11.** Does "Solicitar contrato" replace or sit beside "Guardar cotización"? Recipients (reuse `config_solicitudes.emails`, `config_notificaciones.destinatarios`, or an internal bell list) and channel. Until answered, no notification change.

### 8.1 Design
- **Migration 316** `20260601000316_recuperaciones_consumidas.sql` (numbering checked across all worktrees: 312/313 = #126, 314 = this block, 315 = #127, 316 free): table `public.recuperaciones_consumidas(user_id, evento, estado 'reclamada'|'aplicada', reclamada_en, aplicada_en)` with **PRIMARY KEY (user_id, evento)**, RLS on with no policies, all privileges revoked from `public/anon/authenticated`, granted only to `service_role`. Additive, no data, idempotent. Scripts: `preflight_316…`, `postcheck_316…`, `rollback_316…` (one integral read-only query each, rollback is a plain drop).
- **Event = user + recovery session + recovery instant:** `evento = "<session_id>:<amr recovery timestamp>"`, taken from the access token that Auth verified (`getUser(token)`). A new recovery link creates a new Auth session, hence a new event; an earlier consumed event stays consumed. A token without `session_id` is denied.
- **Atomic claim before the password write:** `restablecerContrasena` = verify token → read claim (page/action fast path) → **INSERT claim** (the primary key lets exactly one concurrent request through; the others get 23505 → "link already used") → `updateUser({ password })` **with no metadata** → mark `aplicada` → revoke sessions. `user_metadata` is never consulted or written for authorization.
- **Auth update outcomes:** HTTP 4xx from Auth (weak/same password, rate limit) = definitive rejection, nothing applied → the claim is **released** so the same recovery can fix and retry. A thrown error, a 5xx or a status-less error = **uncertain**: the claim is **kept** (never unlock a possibly-completed reset), no session revocation, result `{ ok:false, incierto:true }`, and the screen "No pudimos confirmar el cambio" offers *Probar a ingresar* / *Solicitar un enlace nuevo* — never a form to resend the password with the same link. If releasing or confirming the claim fails, the event simply stays consumed (safe: ask for a new link).
- **Page** `/restablecer`: consumed + `aplicada` → the existing partial panel (retry closes sessions only); consumed + `reclamada` → the uncertain panel; both survive a reload. Fail-closed on any read error.
- **Preserved:** current-password change (`cambiarContrasena`, closes "others") and `cerrarSesionesAbiertas` do not touch the new table; the retry still closes sessions without resending the password.

### 13.1 B7 — protected rollbacks vs concurrent writers
- **Defect reproduced first, on the real Supabase Postgres image, with separate sessions waiting on observed lock state** (`real_62/rollbacks_concurrentes.mjs`, cases `V`): with the previously delivered bodies, a writer holding an uncommitted insert is invisible to the guard; the `DROP TABLE` then waits for it, the writer commits, and the table disappears together with the committed row. **Reproduced for all four guarded rollbacks: 322, 318, 319 and 323.** 317 has the same guard-then-modify shape and was hardened too; its old body was not separately reproduced.
- **Fix (same protocol in 317, 318, 319, 322, 323 and the new 324):** one transaction; `lock_timeout` 5 s (10 s in 317, as before); the table lock is taken **before** the emptiness guard (ACCESS EXCLUSIVE; SHARE ROW EXCLUSIVE for 317, which only needs to exclude writers); several tables are always locked in the same order (318: `aliado_firmas`, then `cuenta_cobro_aceptaciones`; 323: `cotizacion_solicitudes_contrato`, then `avisos`). A refusal or timeout leaves data and schema unchanged. The maintenance impact is written in each script header (reads/writes of those tables wait for milliseconds while it runs; 323 also locks `avisos`, a shared table, so run it in a quiet window).
- **Limit stated in the 319 header:** `storage.objects` cannot be locked from a migration; the guard sees only committed files, so an in-flight upload can become an orphan file (no registered logo is lost).

## 14. Round 10 — B5 residual: late Auth completion (2026-11-20)

Source: the «Round 2 re-audit» section of `docs/tecnico/codex-review-b2b-complete-2026-11-20.md` (main checkout) and its probe `codex-probe-b2b-late-auth-2026-11-20.test.txt`. Migration 324 was **rewritten in place** (it has never been applied outside disposable local databases); its numbering and file name do not change.

### 14.1 Cause and policy
My round-9 design treated an in-flight verification older than two minutes as abandoned and let a restart «authorize» discard; the application then called Auth's `deleteUser` after the SQL transaction had released its lock. Elapsed time does not prove that an external Auth request stopped: it could confirm the email between the authorization and the deletion, and cleanup then deleted a confirmed account (the success resolver also kept a `descartando` state that refused completion).
**New policy — age never authorizes a destructive action.**
1. **The database deletes, not the application, and only on the real state.** `p324_borrar_sin_verificar` runs `delete from auth.users where id = … and email_confirmed_at is null` inside the same transaction and under the same registration row lock. Auth's confirmation is an UPDATE of that very `auth.users` row, so the two statements serialize: either the confirmation commits first (the delete finds no unconfirmed row and returns «verificado»; the account stays and is completable) or the delete commits first (the late confirmation updates 0 rows and the late verification fails; nothing confirmed is ever deleted). The window between «authorized» and «deleted» no longer exists, and the intermediate `descartando` state was removed. The application no longer calls `deleteUser` anywhere (a source-level test enforces it).
2. **Unknown outcomes are not rejections.** Only a definitive 4xx answer from Auth counts toward the five attempts. A lost response, a 5xx or a timeout releases the reservation without counting and asks the database (the authority) whether the email was confirmed: if so the registration completes, otherwise the person is asked to retry. Reservations that are never resolved (process killed) are released after two minutes **without becoming failures**; time now decides only whether to wait, never whether deletion is safe.
3. Five definitive rejections still discard the never-verified account (attempt limit preserved), now inside the database call that records the fifth rejection.
4. Safe resumption is unchanged (continuation with email + password, idempotent completion); existing users and accounts created before 324 (lazy row, seeded counter) are untouched; the two-minute «recent attempt» check remains only as a courtesy («otro intento en curso») for liveness.
5. Smaller hardening found while testing: row creation tolerates an account deleted concurrently (answers «sin_cuenta» instead of a foreign-key error); resend refuses accounts that no longer exist; the state table now references `auth.users` directly; preflight/postcheck verify that the function owner may delete from `auth.users` (Supabase's migration role does); `rollback_324` also drops the new helper.
