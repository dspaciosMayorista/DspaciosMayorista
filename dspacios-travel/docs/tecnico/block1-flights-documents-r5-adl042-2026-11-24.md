## 1. What changed in the model

| Codex finding | Fix |
|---|---|
| **A1** — grouping by PNR (and all blank-PNR legs together, key = lowest leg id) | A **contracted service is a saved association on each leg**: `contrato_vuelos.servicio_aereo` (uuid). The voucher key (`vouchers.servicio_clave`) is that uuid. The PNR, the leg order, the lowest id and any name play no part. A round trip with PNR ABC123 out / XYZ789 back is **one voucher** that shows each saved record **on its own leg**; two services with the same or no PNR are **two vouchers**. No passenger-to-leg assignment is invented (the document still says none is registered). Generation without a PNR still works. |
| **A2** — changed/removed groups left obsolete links live; no signal | `vouchers.estado` = `vigente` / `revisar` / `retirado`. A trigger on `contrato_vuelos` flags the voucher of a service **the moment its legs really change** (`revisar`) or when the service has **no legs left** (`retirado`), bumps `revision` (so the existing Gestión «updated / communication pending» signal fires without anyone regenerating) and keeps the row (history). `guardar_vouchers_vuelo` returns a voucher to `vigente` only by storing content built from the legs saved **now**; it **retires** the vouchers of services missing from the payload; all in one serialized transaction. The serving boundary (`resolverAccesoVoucher` + `/voucher/[token]`) **never serves a non-current voucher as current**: an ally (after the owner + 100 % paid checks, so nothing leaks earlier) gets «Voucher en actualización» or «Voucher retirado» with no itinerary, no passengers, no PNR; internal staff get the stale document **with a printed «Desactualizado» banner** (`revisar`) or the retired notice. |

### How a leg gets its service (nothing is guessed at generation time)
1. **Existing writers** (reservation flows, manual contract): a `BEFORE INSERT` default gives all legs a contract receives with no service **within one transaction** the **same new service** (a reservation's legs are one contracted service). Transaction-local setting, no extra reads.
2. **Flight editor** (`guardar_tramos_contrato`, re-created inside 338): each leg carries an explicit `servicio` — empty = keep the saved one; the uuid of **another service of this contract** = **merge**; `nuevo:1…9` = **split / create**. A saved leg with no service must be given one; a **new** leg with no service joins the only service of the payload, and with several services is **rejected** (not guessed). An unknown service id is rejected. UI: a «Servicio aéreo contratado» selector per leg in `TramosEditor`.
3. **Superadmin content editor** (recreates legs, new ids): inherits the contract's single service; with several services (or mixed unassociated legs) it **refuses before touching anything**.
4. **Historical legs (backfill)**: only the unambiguous shapes are associated (one leg, or exactly one outbound + one return). Every other contract keeps `NULL` legs and generation **refuses before any write** with a clear message until staff associate them in the editor. Existing 337 vouchers of unambiguous contracts are re-keyed to that service (same link); the rest become `legado-<id>` / `revisar` (their link stops serving the itinerary until regenerated; nothing is deleted).

### Concurrency and stale reads
`servicios_aereos_contrato(p_numero)` returns each service's uuid, leg ids and a **fingerprint of every saved itinerary field**. The application reads it **before** the legs and sends it back; the RPC (one advisory lock per contract, same key order) refuses with `SERVICIOS_CAMBIARON` — **before writing anything** — if the services, their leg ids **or any saved field** differ from what was read (a same-ids edit of an hour/PNR is caught: found while designing the concurrency scenario, ids alone were not enough). The action reports it as «los vuelos cambiaron mientras se generaba… no se cambió nada».

## 4. Limits and things not done / owner-visible decisions
- **Default association is by transaction**: a reservation's legs become one service. Two services contracted together in a single manual contract must be split in the flight editor («Servicio nuevo A/B…»). This is the one place where a default is applied; it is stored, visible and editable, never recomputed.
- **Historical ambiguity needs a human**: contracts with more than one leg that are not exactly one outbound + one return stay unassociated; the preflight counts them (control 8). Until associated, generation for that contract is refused (nothing breaks otherwise).
- A retired voucher stays visible as history (internal «Retirado» badge, Gestión «vuelo desactualizado»); delete it by hand from the panel to clear the flag.
- A «revisar» voucher shown to internal staff is the **stale** document with a printed banner (the owner asked to retain history; it is never presented as current).
- The full historical Gestión suite (`gestionContratos106.pg.ts`, needs the `g106_base` template) was **not** re-run; G1–G9 of the SQL battery and driver section C cover the voucher semantics changed here.
- Gestión counts a retired voucher as «not current» forever (until deleted); the 309 acknowledgment logic is unchanged.
- **Pre-existing observation, not changed here**: in the disposable databases `eliminar_contrato` is refused by the 284 identity guard for a contract that still has `contrato_vuelos` rows (the cascade delete of the legs reports «el contrato cambió»). It reproduces on a database WITHOUT 338 and without any voucher. The driver's scenario E5 therefore only proves that 338 changes nothing (same outcome with and without an issued air voucher); whether production behaves like the disposable copy was not checked.
- Found by review while closing the round (fixed, tested): a leg that gets its **first** service (historical unassociated leg joining service S) now flags S's voucher too (SQL C11b, driver B4).
- Deployment order (when approved, not done): preflight 338 → 334–338 in order → postcheck → deploy code. The code needs the column, the helper and the RPC; do not deploy it before the migrations.
