## 2. Design

### 2.1 #11 presence (bounded, not a live connection)

- Table `presencia_usuario(usuario_id pk → usuarios on delete cascade, visto_en)`: one row per person, RLS on, **all privileges revoked** from `anon`/`authenticated`. It is written only by `registrar_presencia()` (SECURITY DEFINER, `search_path = ''`, `execute` to `authenticated` only).
- `registrar_presencia()`: identity from `auth.uid()`; the person must be active and have an internal role or `agencia`/`freelance` (others, inactive users and anon get nothing, no row). Upsert with `where visto_en < now() − 4 minutes` → **server throttle: at most one write per person per 4 minutes**, whatever the client does. Returns `true` only if it wrote.
- Client `components/presencia/PresenciaActiva.tsx` + pure controller `crearControladorPresencia` in `lib/presencia/ping.ts` (mounted in the dashboard layout, the B2B portal shell and the CRM layout): **no timers, no polling, no hidden-tab tracking.** It acts only when the tab is **visible** and the person did something real (page load, return to the tab, click, key press), and at most **once per 5 minutes per person per browser** (the last send is stored under that person's own key and shared by their tabs; reserved before sending, so concurrent tabs do not double send). A failed call retries after 60 s at the earliest (and only on a new gesture); a definitive refusal (not signed in / not allowed) stops sending for **that account** only. The session is read locally (no request) only when a gesture already passed the limit, i.e. at most once every 5 minutes, plus once per return to the tab. The call goes **directly browser → Supabase** (no Vercel function invocation).
- Report `fn_actividad_reciente(p_dias)` (superadmin only; any other caller, inactive superadmin, anon or a service key without actor → `42501`, never an empty list). Returns active internal staff **and** allies (max 100), ordered by last observed presence, with `visto_en`, last audited change, 24 h / window event counts and last sign-in as context. Card `components/dashboard/ActividadReciente.tsx` (server component) groups «Personal interno» and «Aliados B2B (agencias y freelancers)», labels each person's level and prints Bogotá time.
- **Freshness window: 10 minutes.** «Actividad observada en los últimos 10 min» = recent; older levels say «hoy», «antes de hoy», or «sin actividad observada todavía». The card footnote states that it is the last observed instant (browser sends at most every 5 min; the server records at most every 4 min), in Bogotá time, **not a live connection**: a person who just closed the tab can still read as recent for up to 10 minutes, and someone idle on an open tab reads as not recent.
- Known, bounded residual: if the account is switched in *another* tab and this tab neither receives the auth event nor is revisited, a gesture here still counts against the previous account's limit (≤ 5 min), and the account that is actually using the app registers from its own tab. A person who only uses the product through a path that never loads one of the three shells (e.g. a bare public link) leaves no observation; the first observation after sign-in needs a visible page load or a gesture.

### 2.2 #13 in-app alerts (no e-mail)

- **Channel:** existing `avisos` + the global bell `CampanaAvisos` (30 s `sondearAvisos`, already mounted in the dashboard layout). The bell was also added to the CRM header, because the CRM is a separate shell. New `avisos.tipo` value `compra_por_vencer`; the other types are untouched. The browser-notification/sound behavior of the bell applies as it does for the existing types.
- **Event key:** `(ventana_tipo, ventana_id, compra_fin)`; a unique partial index over live rows (`archivado_en is null`) makes it impossible to create two live notices for the same deadline event for the same person. Columns added to `avisos`: `ventana_tipo`, `ventana_id`, `ventana_ref` (where to navigate), `ventana_titulo`, `compra_fin`, with a coherence check.
- **Generator** `generar_avisos_compra(p_hoy, p_dias)`: one SQL statement per call with **progress** (B3-3): `e` = all eligible windows (read, uncapped) → `faltan` = (window × recipient) pairs with no live notice → at most 500 inserted in a stable order (deadline, kind, id, person) → `obsoletos` = live notices whose window is no longer eligible → at most 500 archived. It returns `ventanas` (all eligible), `creados`, `archivados`, `pendientes` and `truncado = pendientes > 0`. The **existing** cron route `/api/cron/notificaciones` repeats the call (≤ 20 passes, stops when nothing is pending or a pass made no progress; no new cron or route). `service_role` only. Idempotent: a pass over a complete state writes nothing. Archival never waits for the eligible set to be small or complete.
- **Eligible windows** (same rules as the Paquetes panel): `hoy ≤ compra_fin ≤ hoy + días` in Bogotá; paquete active; salida dinámica active with an active package; empaquetado active with at least one active package; paquete dinámico total active **and** published.
- **Recipients and permission:** active users with role `superadmin`, `gerencia`, `administracion` or `operaciones` (the roles that can write packages, `ESCRITURA.producto`), in the window's tenant (`superadmin` receives from any tenant). `venta`, flight control, allies and unauthenticated users never receive or see them; `sondearAvisos`/the listing also filter the type by role on read, so a stray row cannot reach them.
- **Threshold:** `config_notificaciones.dias_anticipacion` (default 5, clamped 0–365) — **reuse of an existing value** (see §6 policy questions).
- **Links:** every notice opens the affected purchase window: paquete → `/dashboard/paquetes/{id}?tab=config`; salida dinámica → `?tab=vuelos`; empaquetado → `/dashboard/vuelos/empaquetados/{id}`; paquete total → `/dashboard/paquetes/total/{id}`. Centralised in `rutaVentana`.
- **Text:** computed on read against *today* (Bogotá), so a notice created three days ago says «Vence mañana» today, and «Venció» if the daily archive has not run yet: `Compra por vencer · paquete: {nombre} · Vence en 3 días (28/11/2026)` (the kind is spelled out: paquete / salida dinámica / empaquetado / paquete dinámico total).
- **Lifecycle rules:**
  - *Date changes:* triggers on the four sources archive the live notice immediately when `compra_fin` changes or the source (or, for salidas, its package via `ventana_ref`) is deactivated; the next daily run creates the new event. The browser test shows 6 → 5 (archived) → 6 (new event), never 7.
  - *Package deactivated:* archived at once; the daily run does not revive it; reactivating it brings the notice back on the next run (events are keyed by date, not by history).
  - *Deadline expired:* the daily run archives it; between midnight and the cron (08:00 Bogotá) the text already says «Venció».
  - *Indirect cases* (e.g. a package loses its last active package link without a date change) are reconciled by the daily run (now also while more than 500 windows are eligible): stale window ≤ 24 h, plus the 20-pass bound if more than 10,000 stale notices exist at once.
  - *Already read:* reading marks only that person's notice; a changed date creates a new, unread event.
- The Paquetes page keeps the same-rules panel (`AvisosCompraPaquetes`, capped at 200 per source, with the truncation note) and the per-package «Compra: vence en N días» chip; it now reads the eligibility inside the query (B3-2).

### 2.3 #36 + B3-1 + B3-2

- States (`lib/paquetes/estadoPublicacion.ts`, pure): published, published with notices, pending, outdated, generating, error, per-unit quotation, on request, published-but-hidden (inactive/blocked), no vendible offer, **offer not verified**. Unknown input is never «published».
- **B3-1:** the loaders `cargarHotelesBernaloDescubiertos` / `cargarHotelesBajoSolicitud` return an explicit failure flag; when either failed the page passes `ofertaSinVerificar` and the package renders «Oferta sin verificar — no se puede afirmar que no tenga oferta vendible». Authoritative states (pending, error, outdated, inactive) are never overridden. The secondary chip «Unidad sin verificar» appears next to known evidence.
- **B3-2:** `cargarVencimientosCompra` pushes `activo`/date/linkage filters into the query (`!inner` joins) and applies the cap afterwards; truncation is reported independently of the list length, so an empty list with `truncado` renders «La revisión quedó incompleta …». A read error renders its own error notice.

## 6. Policy still unresolved (not invented)

1. **Recipients.** Implemented: the four roles that can write packages, within their tenant (superadmin across tenants). Owner decision needed: should `venta` (who sells these packages) or only named people receive them? Should a per-user opt-out exist?
2. **Threshold.** Implemented: reuse of `config_notificaciones.dias_anticipacion` (default 5) shared with the CxP/instalment/flight-block digest. Decision needed: one value for everything, or a separate package threshold; and whether a second reminder (e.g. 1 day) is wanted.
3. **Expiry/deactivation.** Implemented as in §2.2; staleness ≤ 24 h only for indirect cases (a package losing its last active link). Decision needed if that window is unacceptable (it would need a trigger per link table).
4. **Presence.** Is the 10-minute freshness window acceptable? (Constants: client 5 min, server 4 min, window 10 min.) Should presence also be recorded for `cliente_final` / public viewers? (Not implemented.)
5. **CRM bell.** The bell was added to the CRM header so the notices are reachable from every screen the team uses; confirm.
6. **Block 2 interaction.** Migration 340 also rewrites `avisos_tipo_check`; 343 rebuilds it from the current definition and appends its type, so the **apply order must be 340 then 343**. Block 2 also edits `lib/avisos/*` and `CampanaAvisos.tsx`; the 343 edits there are additive, and the bell-panel class is identical to block 2's.
7. **Hosted costs** are not measured (local evidence only, §7).
8. **Round-2 bounds to confirm:** 500 notices created / 500 archived per call and at most 20 calls per daily run (10,000 notices); the rest is carried to the next run and reported as `pendientes`. A recipient or window created later is picked up by the next run, not instantly. A burst of notices also feeds the bell's existing browser-notification claim (20 per poll), unchanged.
