## 1. V5-1 — the race, and how it is closed

**Why it was real.** Round 5 serialized generations against each other (advisory lock) but a flight edit never took that lock: an edit could commit between the RPC's validation and its UPSERT, flag the voucher `revisar`, and the stale generation then wrote `vigente` over it. Codex's probe reproduces exactly that; my own driver could not have caught it because its pause was at the HTTP layer, *before* the RPC.

**Fix: one lock protocol shared by the generation and every leg writer** (migration 338, `fn_tramo_candado`, `bloquear_voucher_vuelo`):
- One advisory lock per contract (`hashtextextended('voucher_vuelo|'||numero,0)`).
- **Generation** takes it first (`bloquear_voucher_vuelo`: `ventas … FOR KEY SHARE`, then the advisory lock) and holds it to commit: nothing can change a leg between «validated» and «written».
- **Every writer of a leg** takes it in a `BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW` trigger on `contrato_vuelos` (named `t_00_…` so it fires before the default-service trigger), whichever path wrote (flight editor, content editor, reservation flows, traslado de sillas, plain SQL). It is held to that writer's commit. Result: a generation either finishes first (and the edit then invalidates it) or waits for the edit and validates against it. Insert, delete, service reassignment and renumbering (two contracts, fixed lock order) are all covered because the trigger covers all three operations.
- **Deadlock avoidance — global order: `ventas` row first, advisory lock second.** The flight editor already locks `ventas FOR UPDATE` before touching legs; the generation takes the key share before the advisory lock; a plain leg writer takes the advisory lock and only later the key share its FK needs (key shares do not conflict). Before choosing this order I found the opposite order (advisory first) would deadlock against the editor (editor: `ventas FOR UPDATE` → advisory; generation: advisory → FK key share on `ventas`), which is why `bloquear_voucher_vuelo` takes the key share itself. It is `SECURITY DEFINER` only so roles that cannot read `ventas` (venta) take the same locks, and it locks nothing for a contract the caller cannot see.
- The fingerprint check from round 5 stays (it covers the application-read → RPC window).

**Real two-session regression, paused AFTER the fingerprint validation and BEFORE the voucher write** (driver group f2, scenarios V1–V7). The pause is inside the database: a test-only BEFORE trigger on `vouchers` (fixture) waits on advisory lock 981338 held by a separate blocker session. The driver proves the position of the pause from `pg_locks`/`pg_stat_activity` (generation holding the contract lock and waiting at the barrier; the edit queued behind it), runs the real editor action meanwhile, then releases the barrier:

## 2. V5-2 — every rendered itinerary field invalidates (legacy included)

**Why.** Round 5's trigger compared a hand-written list of modern columns; the legacy single-row fields the builder renders (`vuelo_ida`, `vuelo_regreso`, outbound/return times, `fecha_regreso`) were missing, so an issued legacy voucher stayed `vigente` with old content.

**Fix: no field list at all.** `huella_servicio_aereo(numero, servicio)` = md5 over the **whole saved row of every leg of the service** (`to_jsonb(c)` minus the contract number and the absolute `orden`), in **display order** (`orden, id`). Generation stores it on the voucher (`vouchers.huella`, validated against the current one inside the RPC); the leg trigger compares the service's current fingerprint with the stored one on every UPDATE and flags `revisar` when they differ. Consequences: modern fields, legacy fields and any column added later are covered by construction; a save that rewrites identical values is a no-op (fingerprint equal); **display order** is covered by rank — swapping two legs flags, renumbering `orden` without changing the order (e.g. the editor normalizing 20,21 → 0,1) does not. (My first V5-2 attempt compared the whole row including `orden`; the driver caught the false positive on the editor's own normalization — D1 and V3 «surviving service stays current» failed — which is why `orden` is compared by rank.) INSERT/DELETE/service moves still flag unconditionally.
The read helper `servicios_aereos_contrato` uses the same function, so generation-time and trigger-time fingerprints cannot diverge. Existing 337 vouchers are backfilled with the current fingerprint when they are re-keyed.

**Proof through the real path.** Contract DTM-9535 (legacy single row, paid ally; real action to generate): for each of the 7 fields — `vuelo_ida`, `vuelo_regreso`, `hora_salida_ida`, `hora_llegada_ida`, `hora_salida_reg`, `hora_llegada_reg`, `fecha_regreso` — an identical rewrite flags nothing; a real change makes the OLD url non-current **before** regeneration (ally `no_vigente`, staff `revisar`), raises the Gestión signal («actualizado» + 1 voucher not current), and regeneration restores the new value **at the same link** (value checked in the served content). Order swap/renumbering checked on DTM-9527. Viewers who must not see it get nothing: unpaid ally → `pago_incompleto` (not even «no vigente»), colleague venta and the other agency refused; the changed legacy voucher of the unpaid contract is still flagged `revisar` for staff. Compiled output below.
The only write paths exercised for legacy columns are plain SQL updates (what a migration/operator does) — **the traslado de sillas RPC, which also rewrites those columns, goes through the same trigger by construction but was not run end to end here.**

## 4. Limits, trade-offs and things not done
- **Waiting.** A generation now waits for a flight editor save in progress on the same contract (and vice versa) instead of racing it. Under the role's 8 s `statement_timeout` a very long editor transaction could make a generation fail with a timeout (reported as an error, nothing written). Not measured under real load.
- **The lock covers writers that go through `contrato_vuelos` triggers.** `TRUNCATE`, `session_replication_role = replica` or a restore bypass it; none is a supported write path.
- **Voucher content also depends on contract data that is not a leg** (passengers, titular, vendedor). Changing those does not flag the voucher and is unchanged from rounds 4–5.
- **A leg edit that is later undone** (net no-op across several statements) leaves the voucher `revisar` until regenerated; regeneration with identical content keeps the link and does not raise a notice.
- **Not run end to end:** the `traslado de sillas` RPC (it rewrites legacy columns; it hits the same trigger and lock by construction); the full historical Gestión suite; the 22-file sweep failure from round 5 remains unclassified.
- Deployment order unchanged (preflight → 334–338 → postcheck → deploy code); 338 is still unapplied outside disposable databases, so it was changed in place.
