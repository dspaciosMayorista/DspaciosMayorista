## 1. O-1 — the hotel age-configuration diagnostic is internal-only

**Reproduced first (static + live):** `TarifarioPublic.tsx` / `VistaBooking.tsx` render the `hoteles-en-revision` block with no role condition, and both search actions returned the detailed `motivo` to any caller (field names «Infante hasta»/«Niño hasta» and «Producto → Hoteles → Configuración del hotel»). Besides search, the same text also left the server through the reservation compute (`computo.ts`, reachable by an ally who reserves), the hotel-on-request evaluation (`solicitudHotelServidor.ts`) and the hotel modal's client-side validation (`VistaBooking.tsx`).

**Implementation (server decides, using the real session; sanitizes the payload, not only the UI):**
* `lib/tarifario/detalleInterno.ts` (pure): `tieneDetalleInterno(rol, activo)` **reuses `canalDeRol`** (the same rule the comparative quotations and the public card already use: internal role AND active account; anonymous, `agencia`, `freelance`, `cliente_final`, inactive internal = external). `sanearBusquedaHoteles(r, interno)` removes, for externals, the `enRevision` list and a `diagnostico` that describes configuration, and always strips the internal marker `diagnosticoConfig`. `traeDetalleInterno(r)` says whether there is anything to hide.
* `lib/tarifario/detalleInterno.server.ts`: `peticionConDetalleInterno()` — one Auth read + one read of the caller's own `usuarios` row **per search, never per hotel**; **anonymous visitors cost zero queries**; any failure resolves as external (fails closed).
* `buscarHoteles` (`reservar/actions.ts`, the browser-reachable action) calls the session reader **lazily — only when the engine result contains configuration detail** — then sanitizes. The engine (`lib/reservar/cotizar.ts`) keeps full detail internally and now tags which `diagnostico` is configuration-derived (`diagnosticoConfig`); it is not exported as a server action.
* `buscarAlojamientosUnidadPorFechas` (unit hotels) returns `enRevision: []` to externals; one lazy session read only when there is a blocked hotel.
* Reservation/solicitud/modal paths use the new neutral text `MENSAJE_EDADES_HOTEL_PUBLICO` («Este hotel no está disponible para cotizar con menores en este momento. Consulta con un asesor o cotiza solo con adultos.»); the detail goes to the server log only. The public Bernalo quote already mapped this code to a fixed message; it now reuses the same constant.
* **Safety rule unchanged:** a hotel without valid ages is still not quoted with minors (the hotel is simply not listed); adults-only searches and Adults Only handling are untouched. Internal staff still get the full actionable message in the search UI and in the product editors.

**Tests:** `pruebas/detalleInternoHoteles1262.test.ts` (11): roles incl. inactive/null, sanitizer (serialized external payload contains none of «Infante hasta», «Niño hasta», «Producto →», «Configuración del hotel», `enRevision`, `edades_hotel_incompletas`, the hotel name), lazy-read predicate, wiring of both actions, fail-closed reader, public wording. Adapted (not weakened): `edadesNocheReferencia.pg.ts` (reservation error is now the public text, asserted not to contain field names), `busquedaPorcionTerrestreWiring.test.ts` (new return line).
**Real roles in the final build (`guion_o1_o4.mjs` O1, review database, read-only): 109 OK / 0 FALLO** across visitor, `freelance@`, `aliado@`, `administracion@`, `superadmin@`, in Vista Booking and (for staff) Vista tabla, person (CARTAGENA O3) and unit (CARTAGENA U1) destinations: externals — no «hoteles en revisión» box, no «Infante hasta / Niño hasta / Producto → / Configuración del hotel» on screen **or in any Server Action response body** (non-empty `enRevision` absent); staff — box, message and payload detail present. Adults-only searches list all hotels for everyone; the Adults Only hotel remains available/refused as before; the hotels without valid ages are still never listed with minors. ## 2. O-2 — readable adult/child breakdown for unit-priced accommodation

**Pure function** `desgloseInformativoUnidad` (`lib/reservar/cargosMenoresUnidad.ts`): `total = base of the unit (includes minors without their own charge) + own charges of minors`; the **equivalent per adult = base ÷ adults is offered only when honest** — all rooms the same accommodation with the same adults (same tariff) and **no minor who pays as an adult**; otherwise only the base is shown (never an average of different tariffs, never a person tariff). Incoherent data (charges > total, no rooms) renders nothing. The unit price stays authoritative: nothing in pricing, saved quotations, accounting or document grouping changed; the component only reads data already in the payload.
**Owner's example** (2 adults, child 8 charged 150.000 for 3 nights, infant 2 without charge, total 750.000): base **600.000** (includes 1 minor without own charge) · «2 adultos · equivalente informativo ≈ 300.000 c/u (base ÷ 2; el precio real es por unidad, no por persona)» · «+ Cargos propios de menores (ya suman al total) 150.000» · **Total de la reserva 750.000**. The per-minor lines of #126-B remain.
**Surfaces:** table cell and card (both from the search payload, no new request); **modal** — the public quote result gained one deliberate key `menores` (edad/clase/cobro/importe de venta, copied field by field from `cargosMenoresUnidad`; no net, gross, commission or snapshot) and the modal replaces the naive «≈ por viajero» average with the breakdown (the average remains when there is no breakdown). `cotizacionBernaloWiring.test.ts` (closed-key-set test) was updated from 6 to 7 authorized keys on purpose.
**Tests:** `desgloseUnidad1262.test.ts` (9, pure: owner's example, adults only, included minors, per-night vs per-stay, different rooms, equal rooms, pays-as-adult, incoherent data, USD) and `desgloseUnidad1262.react.ts` (6, real table component: owner's example text, different rooms, pays-as-adult, USD without COP, adults only, incoherent). `tablaUnidad102.react.ts` assertion «no c/u» was **deliberately replaced** by «equivalente informativo… no es por persona» and «no Tarifa de adulto».
**Real rendered output (final build, O2): visitor in Vista Booking and `administracion@` in Vista tabla and Vista Booking, destination CARTAGENA U1, 2 adults + minors 8 and 2:** «Niño de 8 años: cargo propio $ 150.000 en total (se cobra por noche, 3 noches…)», «Infante de 2 años: sin cargo propio (tarifa $0 del hotel)», **base 600.000 + cargos 150.000 = total 750.000**, «2 adultos · equivalente informativo ≈ $ 300.000 c/u (base ÷ 2; el precio real es por unidad, no por persona)» — exactly the owner's screenshot case, total unchanged. **The modal was NOT exercised live** (no real-browser run of the quote editor): it is covered by source wiring, the public-payload key test and the shared component test only.

## 3. O-3 — request → staff → proofs → passengers → contract (traced and reproduced)

### What exists (code trace)
1. Ally request: `solicitar_contrato_cotizacion` (323) on a **quotation**; event + in-platform notice only to configured recipients; link `/dashboard/cotizaciones/<id>`.
2. A quotation created by the ally through the **checkout** (`crearCotizacionCarrito`) stores **the titular only** (`payload.cliente`: names, document type/number, phone, e-mail) and `payload.pasajeros = []` **by design**. The ally portal and checkout have **no passenger list**; `/dashboard/reservar/*` is not reachable by `agencia`/`freelance` (`LECTURA_MODULO`). Quotations created by **staff** through Reservar *do* carry passengers (`payload.pasajeros`) and the conversion uses them without any capture panel.
3. Payment evidence: `contrato_soportes_pago` (#86) belongs to **contracts**: the ally can attach evidence only to a contract with at least one registered payment («Soportes vigentes: N de M pagos registrados»); a support is **not** a payment. A pre-contract prepayment is a **staff-registered** fact (`cotizacion_pagos_previos`, no file) transferred to an abono at conversion.

### Reproduction on the delivered build (read-only, review database)
* **C-REV78** (seeded with an empty payload `{}`): opening «Confirmar → generar contrato» shows **2 blank passenger rows** (nothing precharged) — this is what the owner saw. Cause: **a seed artifact** (the sample quotation never had a titular or passengers), not a loss of ally data. It is left untouched (the reviewed record is preserved).
* **C-0005** (real quotation with 4 passengers): **no capture panel** — the saved passengers are used without retyping.

### Defect found and fixed in the normal flow
The conversion form of a **cart** quotation prefilled passenger 1 from the titular but **always set the document type «CC»**, discarding the type the ally chose at checkout (the contract's titular kept the chosen type, so the two disagreed). Now passenger 1 carries the titular's type (`CotizacionAcciones` already did this): a type the reservation does not accept for a passenger (NIT/PPT) leaves the document to capture instead of inventing one; without a chosen type it stays «CC». Test: `convertirCarritoTitular1263.react.ts` (4).

### Do the two remaining gaps prevent the owner's requested flow?
* **G1 (no proof stage before the contract): YES for the requested behavior** «uploaded payment proofs must be visible to the authorized reviewer *before* confirming the relevant payment/contract stage». Today evidence can only be attached to a contract **after** staff registered the payment, so the proof cannot inform that registration, and nothing pre-contract exists. The request → notice → quotation → conversion → contract path itself **works**; the proof-first requirement is **not met** and is not claimed.
* **G2 (no ally passenger list): PARTIALLY.** It does **not** block conversion (titular arrives as passenger 1 without retyping, now with the chosen document type; the others are typed by staff, nobody is invented), but the requested «if the ally already entered passengers, staff receive them without retyping» can only hold for the titular — allies have nowhere to enter more. Quotations staff create in Reservar do carry passengers and convert without retyping.
* Neither gap is closed by this work; both need owner approval and a migration/UI extension (proposals below).

### Bounded gaps (identified, **not** implemented, not claimed as passing)
* **G1 — no proof stage before the contract.** The ally cannot attach evidence to a quotation/request, and a proof cannot precede the registration of the payment it supports; staff register the payment first. **Minimum proposed extension (needs owner approval + a migration):** let the ally attach up to N files (PDF/JPG/PNG, same byte-level validation, private bucket) to the **open contract-request event**, shown read-only to the authorized reviewer on the quotation page («Evidencia adjunta por el aliado — no es un pago»); staff still register the prepayment (`cotizacion_pagos_previos`) as today; at conversion the files are **linked** to the new contract's supports without creating abonos; no minimum, payment or voucher rule is waived; support verification and contract generation keep their distinct meanings.
* **G2 — no ally passenger list in the normal flow.** If the owner wants allies to supply passengers when requesting, the minimum is an optional passenger block in the checkout persisted in `payload.pasajeros` (the conversion already consumes it) — not built, because it changes what allies must provide.

### Real findings while executing O-3 (pre-existing, not introduced here; none fixed — they are outside the owner's O-1…O-4 list)
* **F1 — `administracion@`/`gerencia` cannot pick the required advisor when converting.** The conversion screen lists advisors from `usuarios` (role `venta`) under RLS, and the only policies are «own profile» and «superadmin»; for those roles the list is **empty** while the advisor is **required** («Elige el asesor interno que gestiona esta reserva»). The recipient of the request notice (`administracion@`) can open the quotation but **cannot generate the contract**; `superadmin` (advisor optional) or the `venta` advisor can. Verified in the real UI and with `pg_policies`.
* **F2 — a titular document typed with letters under «CE» is refused at conversion** («El documento debe ser solo números (excepto Pasaporte)»): the checkout accepted `E1234567`; the conversion validation (digits only for CC/CE/TI/RC) correctly stops it, so staff must correct the number. The walkthrough therefore uses `1234567`.

## 4. O-4 — «Olvidé mi contraseña» from «Continúa tu registro»

* The «Continúa tu registro» step now has **«Olvidé mi contraseña»** (a link to `/recuperar?desde=registro`). Clicking it stores a **draft of the form fields only** (whitelist; never password, confirmation or code) in the same browser, valid 60 minutes (`lib/auth/borradorRegistroB2B.ts`).
* `/recuperar?desde=registro` prefills the e-mail from that draft and otherwise behaves **exactly as before** (same `resetPasswordForEmail` with `redirectTo …/auth/callback?next=/restablecer`, same generic answer for any e-mail, same rate-limit handling); it adds a sentence that the person returns to «Continúa tu registro».
* After the audited reset succeeds, `RestablecerClient` goes to `/portal/registro?retomar=1` **if a valid draft exists** (else `/login?clave=1` as before). `RegistroForm` restores the data, shows «Contraseña actualizada…», and **requires typing the new password** (never precharged); continuation is still `continuarRegistroB2B` = real Auth password check → `registro_b2b_completar` (idempotent). Success clears the draft.
* **Untouched:** server recovery rules (reclaim, B1–B5), generic responses, no retroactive verification, no login/auth bypass, consumption (no new requests; only a `localStorage` write on the click and one read per screen).
* **Tests:** `registroOlvideContrasena1264.react.ts` (9) with the real components and stubs; **real GoTrue + Mailpit execution on the disposable copy, final build: 20 OK / 0 FALLO** (`continuar2@revision.test`): «Olvidé mi contraseña» present → `/recuperar?desde=registro` with the e-mail prefilled, generic message (identical for an unknown e-mail) → recovery e-mail arrives → link opens `/restablecer` → password changed → returned to `/portal/registro?retomar=1`, «Continúa tu registro» with «Contraseña actualizada», **password field empty**, **no request yet** → the **old** password does not continue and creates nothing → the **new** password creates **exactly one** request; `email_confirmed_at` unchanged, account still inactive, no second request on revisiting; and requesting recovery for a registration that was **never verified** neither verifies it nor creates a request.
* **Real defect found and fixed by this run:** a pending registration is **inactive by design**, and `proxy.ts` bounced any inactive session to `/login?inactivo=1` **before** `/restablecer`, so the recovery link could never reach the password form (the component tests could not show it). Fix (one line, `proxy.ts`): the profile read — which drives that bounce and the external-role redirect — is also skipped for `/restablecer`. The page only offers a password change; the action still requires the verified recovery session in the server; the route is still not public (needs a session); an inactive account still has no role and no data access. Tests: `borradorRegistroB2B1264.test.ts` (+2 wiring assertions on this), proxy-related suites (62/62). **This touches the audited session/inactive rule — flagged for Codex.** **E.3 (brand-new registration with a typed code) remains an OWNER check; executor tests are not owner acceptance.**
