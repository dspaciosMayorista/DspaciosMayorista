### H103-04 — what «Aplicar» really does (source evidence)
- `CalendarioExclusiones.tsx` `aplicar()` calls `aplicarConjunto(vigencia, value, conjunto.rangos)` (`lib/hoteles/conjuntosFechas.ts`) and `onChange(r.blackouts)`, i.e. it only mutates the form state `blackouts` of the validity open in `TemporadasBox` (`HotelDetalleClient.tsx`).
- It is saved only by «Guardar cambios» / «Agregar temporada» (`actualizarTemporada` / `crearTemporada`). It never calls a server action (asserted: `G.__cal103.llamadas.length === 0` / `llamadas = []`).
- Only nights inside the validity's ranges are copied; the rest are reported («caen fuera de esta vigencia y NO se copiaron»).
- There is no link set↔validity: editing/deleting the set never changes saved validities (rehearsal step H103-04 asserts it against the DB).
- **It does not create a validity and never selects another saved validity.**

### H103-04 — «create a validity from a set»: exact missing decisions (NOT implemented as persistence)
A validity (`hotel_temporadas`) is not just a name + dates. Fields the system treats as business data: `nombre`, main range + extra ranges (`fecha_inicio/fin`, `rangos`), `prioridad`, `min_noches`, purchase window (`compra_inicio/fin`), `tipo` (`tarifa` | `descuento_pct` | `descuento_monto` | `promo_noche_gratis`) with its own mandatory choices (`descuento_valor`, `descuento_unidad`, `noche_gratis_regla`, `dias_promo`), `regimen_restringido`, payment condition, and — crucially — **the rates live in other rows** (`tarifa_hotel.temporada` is a name string, no FK). A validity row with no rates sells nothing. I found no draft/inactive flag on `hotel_temporadas` (migrations 016/038/053/083/123/164/300/310), and saving a validity triggers regeneration of the published tarifarios (`regenerarDespues`), so persisting an incomplete one would have side effects on live packages.
Decisions the owner must make before a «create from set» that persists:
1. Dates: a set has nights, not the validity's travel range — where do the validity's dates come from (a range typed by the user is required)?
2. Rates: copy from which existing validity (name), or leave empty (a validity without rates)?
3. State: should an incomplete validity exist at all (needs a draft/inactive flag = migration + engine changes so it never sells or regenerates)?
4. Type/priority/purchase window defaults.
**Implemented proposal (pure UI, nothing persisted):** «Empezar una vigencia nueva con este conjunto» pre-fills the *new validity* form with the set's name and nights; the person completes dates/type/rates and presses the normal «Agregar temporada» (which keeps all existing validation). If the owner wants persisted drafts, answer 1–4 above.

### H103-13 — how the supplier message can be edited (explained from source)
- **Before this change: hard-coded.** Subject `asuntoSolicitud()` (`lib/solicitudProveedor/nucleo.ts`): `Solicitud de servicio · {proveedor} · Reserva {número}`. Body `construirCorreoSolicitud()` (`lib/solicitudProveedor/documento.ts`): greeting, the fixed sentence «Les enviamos la solicitud de servicio de la reserva … Por favor respondan a este correo confirmando el servicio o indicando cualquier cambio.», the promotion-code box, the «SOLICITUD DE SERVICIO» table and the Alojamiento / Servicios / Pasajeros tables, built from reservation data. The payment notice `construirCorreoPago()` (`lib/solicitudProveedor/avisoPago.ts`) likewise. There is **no template table, no per-agency text setting, no admin screen**; configuration is only environment variables for transport (mode, sender, reply-to, capture URL).
- **Reconciled with the approved design:** a structured message with tables, not the customer's voucher, no PDF required (the payment notice attaches payment proofs only). Unchanged.
- **Smallest practical approach (implemented):** a single optional free-text field per send («Mensaje adicional para el proveedor (opcional)», ≤ 600 characters, plain text) in the send form of `SolicitudesProveedorPanel` and of the payment notice (`pagos/avisos/AvisosPagoClient`). Properties, all tested:
  - rendered **after the greeting/intro and before the code box and the tables**, in HTML (escaped, line breaks as `<br>`) and plain text (raw);
  - validated on the **server** (`limpiarMensajeAdicional`: trims, CRLF→LF, drops control characters, 601+ is an error — never a silent cut) in preview and send;
  - frozen with the message (`payload.html/texto`, `snapshot.datos.mensaje`), so retries/«Reintentar envío» resend the same text;
  - **absent note ⇒ byte-identical old message and unchanged idempotency key** (the key is built from `datos`, and `mensaje` is only present in `datos` when written): proved by removing the note paragraph from the new output and comparing with the note-less output, both pure and against captured Mailpit messages; a blank note equals no note (an already-sent identical request is not re-sent); a different note is a different request;
  - never replaces the tables, the promotion code (still enforced), the supplier identity, the payment relations or attached proofs; the Reply-To token and the reply-vs-confirmation behavior are untouched (a reply to a note-bearing request is still only «respondida»; the human decision stays separate);
  - changing the note after a preview switches **send off** until the preview is regenerated (supplier panel: the hotel/code controls are kept, only the preview becomes stale; payment screen: the preview is dropped like for any other field).
- **Alternative NOT implemented (owner decision):** a stored default template per agency with placeholders (`{{reserva}}`, `{{proveedor}}`, …) editable by superadmin. Cost: a new table + migration + RLS + audit, a settings screen, placeholder validation/escaping, per-send rendering of the template with the same idempotency/freeze rules, migration of the existing frozen payloads' meaning, tests for every placeholder, and decisions on who may edit, versioning and per-supplier overrides. The per-send note covers «add a sentence» without any of that; it does not allow changing the fixed sentence, the subject or the table columns.
