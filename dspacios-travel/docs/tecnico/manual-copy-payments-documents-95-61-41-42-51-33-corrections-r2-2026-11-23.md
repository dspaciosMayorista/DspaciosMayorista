## 1. R2-1 — fail closed on minimum sources; authoritative database validation

**What was wrong (confirmed):** `generarPlanCobro` ignored the error of the `contrato_condiciones` read and of `config_cobros` (`pctAbonoDe` fell back to 30 %), and migration 332 took its sum-check target from the caller-controlled `p_fuentes.total` and compared neither conditions, configuration nor currency inputs.

**Correction**
- Action (`app/(dashboard)/dashboard/contratos/[numero]/cobros-actions.ts`): a failed read of `contrato_condiciones` or of `config_cobros` stops BEFORE any calculation or database call («No se pudieron leer las condiciones de pago…» / «No se pudo leer el porcentaje de abono configurado…»). Verified ABSENCE of a configuration row (read succeeded, no row) still means the historical 30 %. `pctAbonoDe` is no longer exported (it had no other caller). The action now also sends `moneda`, `moneda_cobro`, `trm_cobro`, `moneda_efectiva` and the effective `pct_abono` it used.
- Database (migration 332): `plan_cobro_fuentes` now DERIVES, from the contract row, the total to collect and the effective collection currency (mirror of `cobroDeVenta` / `p75_priv.regla_confirmacion`) and the effective minimum percentage using the single rule `p75_priv.regla_confirmacion` (agreement → frozen conditions → `config_cobros`), i.e. it reads `contrato_condiciones` and `config_cobros` itself. `reemplazar_plan_cobro` re-reads all of it under the per-contract advisory lock and rejects with `PLAN_COBRO_FUENTES_CAMBIARON` if payments, agreement id, price, collection total, collection TRM, either currency, departure date, derived total, derived effective currency or derived percentage differ from what the action used. **The row sum is validated against the database-derived total, not against `p_fuentes.total`.**

## 2. R2-2 — a new optional selection must not release a historical included obligation

**What was wrong (confirmed):** `objetivoIds.has(sid)` made an obligation editable merely because the NEW selection contained that service. Reproduction (previous code, real action): reserve with an included asistencia (60.000 for 2 pax), the package reclassifies it as optional and its catalog price drops to 5.000/pax, then select it as optional → the obligation was rewritten from 60.000 to 10.000 (the audit's 40.000 → 10.000).

**Correction** (`lib/reservar/clasificacionServiciosContrato.ts`, `actualizarServiciosContrato`)
1. The new selection no longer influences editability. An obligation is editable only if the contract's own «Servicio · {name}» line proves it was a chosen optional.
2. A selected service that already has a CONSERVED obligation is reported in `conflictos`, and the action rejects the whole edit BEFORE any write («No se puede agregar como opcional «…»: este contrato ya tiene una obligación con ese servicio… No se cambió nada.»). Nothing is merged, duplicated or lost.
3. Display-name identity: the contract line stores only the name. A name releases money only when it identifies unambiguously — at most as many obligations carry that name as lines exist, and NO other service of the package (by id) has the same normalized name; otherwise the obligation is conserved.

**Evidence**
- Unit (`clasificacionServicios51`, 14/14 incl. the audit input `{id:77, servicio_id:5, 40.000}` with target service 5 at 10.000 → not editable, conflict reported, reconciliation touches nothing; homonym and two-obligations-one-line cases).

  1. real `crearCotizacion` + `convertirCotizacion` with an INCLUDED asistencia: `resumen = 826000|0|60000|true`, obligation `9502:asistencia:60000`.
  2. Package reclassifies the service as optional AND its catalog price drops (60.000 → 10.000), tarifario regenerated, then `actualizarServiciosContrato(n,[asistencia])` → **rejected** with the message above; costs, flag, obligation (still 60.000), lines identical; then `actualizarServiciosContrato(n,[])` (remove) → ok, **60.000 / flag preserved / no optional line**.
  3. Service REMOVED from the package: adding the tour → receptivo 80.000 + asistencia 60.000 both present (obligations `9502:asistencia:60000,9503:receptivo:80000`, line «Servicio · Tour…»), price up by 100.000; removing it → the contract returns **exactly** to the reservation state (`826000|0|60000|true`).
  - Negative control on the SAME driver with the previous rule temporarily restored (`r2_2_control_negativo_clasificador_anterior_raw.txt`): the selection returns `{"ok":true}` and the assertion «obligation 60.000 intact» fails. The hija's payload keeps ONLY the chosen option's catalog metadata (A: `Hotel A:Superior/PC/Doble`; B: `Hotel B:Estándar/PAM/Doble`; the other option's hotel is absent). **Representation of the new catalog metadata (stated clearly, not implied):** it lives in the quotation (madre payload / hija payload / quotation detail).
