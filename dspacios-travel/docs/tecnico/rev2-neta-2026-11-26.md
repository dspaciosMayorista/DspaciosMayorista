### How each cost is stored (traced)
- `ventas.costo_hotel|aereo|receptivo|asistencia|otros`: nominal amounts **in `ventas.moneda`** (offer currency, per 236/H-1). One TRM per contract.
- Pending contract: `contrato_obligaciones_previstas(clase='cxp', clave, payload, materializada_en)`; `payload = to_jsonb(cuentas_por_pagar row)` ⇒ `moneda`, `valor_total` (source currency/amount) and, for USD obligations of the cart route, `trm_costo` + `valor_cop_costo = round(valor_total × trm, 2)`. The payload holds **all columns, null ones too** (important: keys are present with JSON null — see §4).
- Confirmed contract: `confirmar_venta` → `materializar_obligaciones` inserts the payload (`jsonb_strip_nulls`) into `cuentas_por_pagar`; the 236 CHECK validates `|valor_cop_costo − round(valor_total × trm_costo, 2)| ≤ 0.01`; accrual entry `postearAsientoCxP` uses the equivalent (`importeCopCxP`).
- Actual payment exchange rate is a different thing: `cxp_pagos.trm` (rate of the payment day) and #63's `valor_cop_63/trm_63`; collection TRM is `ventas.trm_cobro`. None of them is touched.

## 2. Rule implemented (and the one decision I took)

The cost TRM is **provisional while the contract is pending** (nothing accrued, no payment, no entry) and **frozen when the contract is confirmed** (the CxP is born with it, the accrual entry uses it, 236 immutability stays intact).

- Correction after saving is allowed **only on previstas of a PENDING contract**, only for USD obligations that already carry the pair, by superadmin / gerencia / administración / operaciones (same set and same tenant rule as the RLS «cpp: acceso contable»; `venta`, allies and other-tenant staff are refused).
- Already-confirmed CxP are **not** edited: their equivalent has an accrual entry; changing it means correcting accounting (reversal), which needs a separate owner-approved process (the task forbids rewriting accounting entries). The 236 trigger is untouched.
- Historical USD obligations without a pair (other routes) are **not** given a TRM (it would change their accrual from nominal to converted): the UI states «sin equivalente en pesos registrado (no hay TRM de costos)».
- **Owner decision to confirm (proposal):** if the owner wants to correct a TRM AFTER confirmation, the safe design is a reversal-based correction: reverse the `cxp:<id>` accrual entry and post a new one, record the difference in an explicit «diferencia en cambio / ajuste de costeo» account (ties to #43 «diferencia de cambio», documented as pending in the 236 doc §6), only if no payment/retention exists. Not implemented.

Preflight row 6 checks the md5, postcheck row 7 the new definition, rollback restores the 288 body. Regression: T11 (USD, fails before the fix, passes after) and T12 (COP unchanged).
