### B95-19 — the arithmetic (hand-checked)
* B95-18 (COP): stored `2 × 715.228 + 1 × 150.000` and line `−1`. Adults total `1.430.456 − 1 = 1.430.455` → per adult **$715.227,50** (`2 × 715.227,50 = 1.430.455`); row total `1.580.455` = printed total. No unit-of-currency rounding is hidden anywhere: the stored lines still sum to 1.580.455.
* B95-20 (USD): stored `3 × 477,33 + 1 × 150,55` and line `+0,01`. Adults `1.431,99 + 0,01 = 1.432,00` → 477,3333… per adult. Printed: tariff «USD $477.33» (calculation precision), row total «USD $1,582.55» exact. **3 × 477,33 = 1.431,99 ≠ 1.432,00** — the same property the owner accepted for the cart quotation in #94/#52. Owner confirmation requested (**O-1**); alternatives the owner excluded (visible row, split tariffs) are not used. Two pre-existing places still print the honest split for non-whole-cent tariffs (quotation `TarifaUnitaria`, comparative-sheet `TarifaOpcion`); unchanged, listed in O-1.

## 6. Resources (local, proportionate; hosted cost not measured)
* Per customer-document open (`/contrato/[numero]`, `/c/[token]`): **+2** small service-role reads (`ventas.cotizacion_id`, then two JSON fields of one quotation); no polling, no retries, no loops, no external service. Failure is logged (`registrarErrorTecnico`) and the document renders as before.
* Conversion: +1 insert per hotel inside the existing transaction (typically 1–3 rows); idempotent on retry (tested: second conversion adds nothing).
* Render work: O(rows) in memory, pure functions; no new client component, no new request from the browser.
