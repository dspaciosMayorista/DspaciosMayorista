### Quota decision (explicit, tested)
A rejected support is not vigente, so rejecting **frees its slot**. The correction is an ordinary new support under the **same cap** (no exemption): the chain rejected → corrected occupies one slot. Why no exemption: if the correction bypassed the cap, an ally could (reject frees a slot → upload an unrelated support into it → correct) end above payments + 1. If another support took the freed slot, the correction hits `SOPORTE_LIMITE` (UI shows it disabled with the reason) and the ally can **replace** one of its vigente supports (replace never depends on the cap) — not a dead end. Both the server precheck and the DB enforce it (direct RPC call tested). Open owner question: should a rejected-uncorrected support keep its slot reserved (so nobody can fill it)? Not implemented (would block uploads for an ally that never corrects).

### Financial invariants
`soporte_rechazar`, `soporte_corregir` and the two aviso functions never write abonos, ventas, asientos, CxP or commissions (postcheck item 13 greps their bodies; pg test compares a full hash of venta/abonos/CxP/previstas/comisiones/asientos before and after reject and correct).

### Not done (stated)
- No new internal notice type for «support rejected» (the actor knows; others see it in the card). No in-app ally notice (no ally bell exists): e-mail + portal red box are the notification.
- The audit trigger (`trg_auditoria`, 087) is not attached to `soporte_rechazo_aviso` (re-running its DO block would do it); who/when/why live in the support row itself.

## 6. Resources (local measurements; hosted unmeasured)
Reject action ≈ 1 getUser + 1 profile read + 1 RLS read + RPC reject + (config) + RPC claim + ≤10 mail POSTs (N recipients) + RPC close. No polling, timers or effects added; the retry is user-triggered and DB-capped at 5. Portal soportes tab: +2 reads (rejected ≤200 rows per 100-contract batch, then one `corrige_id in (…)`), only when that tab is opened. Contract page: +1 aviso-state read and +1 name read only when the contract has rejected supports. Mail: one provider send per recipient (Resend per-message cost when `vivo`; unmeasured).
