# #76/#77 — Ally end clients ("Mis clientes") and internal visibility

Owner decision (ADL-039, 2026-11-20): an ally's end clients are associated with that ally; allies are isolated from each other; authorized internal access is preserved; the central CRM (#1) is reused without unnecessary duplication; no historical reassignment by inference. Worktree `.worktrees/portal-b2b-allies`, branch `claude/portal-b2b-allies-block`. Nothing was staged, committed, pushed, deployed, run against remote SQL or sent externally.

## 2. Design (smallest that satisfies the decision)

- **Derived at read time (no copy, no backfill):** a client of ally X = a client name on a contract with `ventas.aliado_id = X` or `b2b_usuario_id` in X's users, or on a quotation whose frozen B2B plan / `aliado_id` is X, or created by one of X's users (email). Legacy contracts that name the ally only as text are NOT listed (no inference); the portal shows a notice when the account is legacy-by-name.
- **Ally address book — migration 322 `aliado_clientes`:** contact data the ally writes (document, e-mail, phone, notes). `UNIQUE (aliado_id, clave)` (clave = accent/case-insensitive name key, same function that groups derived rows), mandatory `autorizacion_datos = true`, tenant stamped from the session, audit trigger attached. **service_role only**: RLS on, no policies, no grants to anon/authenticated (pattern of 316) → no direct PostgREST/RPC path for any user; every access goes through server code that takes the ally from the session.
- **Union:** libreta + contracts + quotations merged by name key inside ONE ally; presentation only, reassigns nothing.
- **Portal `/portal/b2b/clientes`:** list (20/page, search by name/document/e-mail/phone), per-client expandable detail (contracts and quotations), add/edit own clients, short Spanish consent/data note. Agents of an agency read; owner/freelance write. New nav tab "Mis clientes" (`ContactRound`).
- **Staff `/crm/clientes-aliados`** (CRM nav "Clientes de aliados", `Handshake`): choose an ally → same loader, read only. Roles: superadmin/gerencia (both agencies), administración/operaciones (own agency only); `venta`, B2B roles, inactive users and users without agency are denied. The ally id comes from a list loaded server-side and is validated against it. This is where ownership is visible; the existing contracts list is unchanged.
- **Not built (by decision/need):** staff editing of an ally's clients; reassignment; filter inside the 221 contracts list (would need a new RPC version or service-role there).

## 4. Resource / consumption (local measurement; hosted unknown)

- Portal visit: **6 Supabase reads** (1 libreta + 2 ventas + 3 cotizaciones, each fully paginated at 1000 rows; measured by the test's call log) and **0 writes**; no polling, timers or retries; idle = 0. Search/pagination are plain GET navigations. The list is derived in memory per request (bounded by the ally's own contracts/quotations).
- Save action: 1 insert or 1 update + `revalidatePath` + client `router.refresh()` (one page re-read).
- Staff page: 1 aliados list (≤1000) + 1 usuarios lookup (≤200) + the same 6 reads, only after an ally is chosen.
- Database: one small table, one index; no function, no trigger beyond the audit trigger. Vercel: two dynamic routes + one Server Action. Hosted Vercel/Supabase deltas: **not measured**.

## 5. Owner-visible items / risks

- Derived clients group by **name key** inside one ally: two different people with the same name collapse into one row (same limit the CRM contract list documents). Document-based grouping would need the document on the contract rows (not stored with a type).
- Legacy contracts (ally only by name, no ids) do not appear until staff link them; no automatic reassignment.
- The portal nav now has 6 tabs (7 for agency owners). The CSS shares the width evenly; not visually verified.
- The libreta is shared by every user of the same ficha (owner and freelance), but agents under an agency can only read it.
- React test prints harmless jsdom `FormData` TypeErrors on form submit (harness artifact; assertions pass).
