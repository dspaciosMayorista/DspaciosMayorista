## 0.H2 Hostinger HIN-2a / HIN-2b correction (Codex review r3, `codex-review-hostinger-103-r3-2026-11-22.md`)
* **HIN-2a — progress inside a page.** When the budget ends in the middle of a page the cursor now moves down to the highest unhandled uid of that page (everything above it is recorded, skipped or parked), through the same compare-and-swap, using a reserved tail of the budget (`RESERVA_GUARDADO_MS`, 1 s of the 8 s; item work stops at the soft end, saves may use the rest). ### 0.4 Mail route — evidence-based proposal (no provider, MX/DNS, billing or live-mail change was made or is requested)
Documented facts (official Hostinger and Resend documentation read in round 1; **nothing was called live**):
- **Hostinger Agentic Mail API:** webhook `message.received` is authenticated only by a bearer secret (no HMAC) and its payload shape is not documented; the message can then be fetched by id (`GET …/mailboxes/{id}/folders/{folder}/messages/{uid}` returns `messageId`, `inReplyTo`, to/cc, subject, attachments; `…/text` the body; `…/source` the raw .eml; `…/search` supports a header filter). **Sending** returns 204 with no body and offers **no idempotency, no Reply-To, no custom headers**. Plus-addressing is undocumented; catch-all is documented. Business Starter: 1,000 messages/day per mailbox, 25 MB attachments.
- **Resend (already integrated):** `Idempotency-Key` (24 h; 409 on concurrent/different payload — handled as uncertain), HTML + text + attachments, `Reply-To`, Svix-signed events (sent/delivered/bounced). Its `email.received` event carries no body.
Proposal (for the owner/Codex to accept or reject; nothing implemented beyond what exists):
1. **Outbound stays on Resend** — the only path that can guarantee «one retry never makes a second message» (idempotency key) and carry the reply token in `Reply-To`. Hostinger's send cannot give that guarantee, so it is **not** used for outbound.
2. **Inbound replies: use the existing Hostinger mailbox as the reply inbox** (the owner already has it): `Reply-To` = a reply address on that mailbox carrying the token. On `message.received` our neutral webhook endpoint (HMAC/bearer variant to add) fetches the message by id and correlates by `inReplyTo`/token — this is the one thing Resend cannot do (it delivers no body). **No Resend inbound plan or upgrade is needed**, and no MX change is needed if the reply address is on the mailbox's existing domain.
3. **Untested and required before relying on it:** (a) whether the token can ride in the local part (plus-addressing or catch-all) on that mailbox; (b) the real webhook payload (capture once with a test mailbox); (c) Resend's current plan limits for the expected volume. I did none of these — each needs the owner's credentials or live mail. Until then the in-app decision buttons («Confirmar/Rechazar») remain the source of truth for the supplier's answer, which is how the current build already works.
4. Not built: the Hostinger adapter (webhook auth variant + message fetch). It is small once (b) is known; building it earlier would be guessing the payload.
