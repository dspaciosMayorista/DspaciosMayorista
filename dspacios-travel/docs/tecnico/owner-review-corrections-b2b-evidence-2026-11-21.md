## 1. What was implemented (and the decisions behind it)

### Correction 1 — origin by creation, not by plan or modality
* **Root cause.** `cargarCotizacionesPortal` (`lib/portal/b2bPortalServidor.ts`) put into «Asistidas» *every* quotation whose frozen plan (`payload.b2bAsistido.aliado_id`) pointed at the ally, and its docstring said «the frozen plan outranks the author». But an ally who quotes alone also freezes a B2B plan, so every NETO/commissionable quotation she created looked «assisted».
* **Provenance inspected first.** The server already stamps `payload.b2bAsistido.origen` («aliado_directo» when it is derived from the ally's own session, «asistida» when staff with permission assists) and `asistido_por.rol` (`resolverCapturaCarrito` in `app/tarifario/checkout/actions.ts`; the browser cannot set either). The owner's record C-0007 carries `origen = aliado_directo`.
* **Rule (pure, `lib/portal/origenCotizacion.ts`).** Plan present → the sealed `origen` decides; plan without `origen` (format before the field) → decided by the sealing role (an ally role ⇒ direct) and, with no role, **assisted** (the only kind that existed before the field — conservative); unknown value ⇒ assisted (never infer «direct» from data the server did not write). No plan → direct only if the ally's own session created it. The author never overrides a genuine assistance seal (a staff-assisted quotation whose `creado_por` happens to equal the ally's email stays assisted).
* Rows from the plan query carry a plan by construction (tagged `delPlan`), rows from the author query only if the plan says so; one `Map` by id ⇒ one list per quotation; beneficiary isolation unchanged (both queries are still keyed by the ally's ficha / own email); `b2b_modo` / `b2b_total` still come from the frozen plan; the internal provenance columns do not leave the loader.
* Comparativas are classified by their own rule (owner/ally id) and were not touched.

### Correction 2 — compact passenger presentation
* **Ally panel** (`PanelPreparacionContrato.tsx`): rows keep a stable key and an open/compact flag. Saved, named rows are compact («Pasajero N · name · TYPE number · nac. date» + «Faltan: documento, nacimiento» marker + **Editar** / **Quitar**); new, unnamed or invalid rows are open; **Listo** compacts a valid row; a failed save re-opens exactly the rows with errors and names them; a successful save re-compacts. Unsaved edits survive compacting/reopening/removing other rows. The validation message now uses the number the screen shows (the first additional passenger is «Pasajero 2», not «Pasajero 1»).
* **Staff conversion** (`ConvertirCarritoBtn.tsx` cart path and `CotizacionAcciones.tsx` ordinary path), shared pure helper `lib/reservar/resumenPasajeroConversion.ts`: a row is born compact only if nothing blocks generation (names, document rule, minor-with-CC, infant without responsible adult); the summary shows class by age and, for an infant, **its chosen responsible adult**; incomplete-but-not-blocking rows say «Faltan: …». Rows with a blocking problem are open and the guardian selector is visible without opening anything. Rows never auto-collapse while typing; only **Listo** collapses. `generar()` re-opens every row with a blocking problem before any message. A change in another row that invalidates the guardian (e.g. the adult's birth date makes her a child) re-opens the infant's row. Guardian selection stays at staff conversion; nothing moved to checkout.

### Correction 3 — «Agregar pasajero» and the declared universe (explicit decision)
* The cart rule (B12/B13) says the real traveller universe is **neither the max nor the sum** of the units' `pax`. So the new pure module `lib/reservar/universoViajeros.ts` does not invent one:
  * **one independent unit** (one hotel, with or without tours linked to it through `hotelRef`; or a single tour) or an **ordinary quotation** ⇒ **exact** universe = its `pax`; the button is **hidden** when every declared traveller already has a row and **comes back** when a row is removed (a note explains why);
  * **two or more independent units** ⇒ **ambiguous**: nothing is hidden by a computed cap; the button stays until a **safety bound** (sum of the units' `pax`) is reached; the note says the staff confirms the real number at conversion.
* **A defect of my previous delivery surfaced and was fixed.** Migration 325 capped the ally's additional passengers at *max(unit pax) − 1*, which contradicts the rule above (two hotels with different travellers would have blocked legitimate passengers). **Migration 326** replaces only `cotizacion_pasajeros_aliado_guardar` with the same universe rule (same owner / SECURITY DEFINER / `search_path` / grants; no tables or data touched), with preflight → migration → postcheck, rollback and an SQL test.
* Ordinary (non-cart) conversion has no add/remove control (the row count is fixed by `pax`), so there is nothing to hide there; its rows only got the compact presentation.

### Correction 4 — the regular tariff belongs to a passenger
`app/tarifario/desgloseTarifas.tsx`: the child with a benefit is now a visually grouped block (accent border + tint, `data-con-beneficio`) and its note is **inside** the block and names the passenger: «**Niño 1 · 8 años**: tarifa regular ~~$269.000~~ · a pagar **$168.000** c/u · …». The partial-night wording is explicit: «El alojamiento **de este niño** es gratis solo en las noches de la promoción · …; las demás noches y los servicios o cargos retenidos se pagan»; «Niño gratis» appears only when the child truly pays nothing. Adults and the infant carry no note. The table view keeps the label from its own line (`conPasajero={false}`). **No pricing, retained-services or document-grouping code was touched** (verified by file modification times: none of `lib/calc/*`, `lib/reservar/cotizar.ts`, `lib/reservar/computo.ts` or `components/contrato/*` was touched in this batch — the integration worktree carries earlier, unrelated diffs there).

## 7. Addendum — R326-1 (offered capture capacity vs. the 30-passenger save limit)

### Finding and reproduction
The ally panel offered `topeAdicionales(universe)` (31 for two independent services of 16 travelers), while the action rejected lists over 30 and the table CHECK `between 1 and 30` (migration 325, unchanged) would raise 23514 for the 31st. Reproduced as audited: before the fix the SQL function accepted the 31-entry list into the CHECK; the new SQL test fails with that exact 23514 against a function without the limit (mutation below).

### Decision: two different numbers, never conflated
* **Traveler universe** (`topeAdicionales`, exact or ambiguous bound): unchanged, still used by the **staff** conversion screens.
* **Technical capture limit** (`LIMITE_CAPTURA_ADICIONALES = 30`, `lib/reservar/universoViajeros.ts`): a *storage* limit of the ally's list. The panel offers `capacidadCaptura = min(universe, 30)` (`puedeAgregarCaptura`). The CHECK was **not** raised; nothing is truncated.
* **Disclosure before entry** (`notaCaptura`): when the universe exceeds the limit the panel says what the quotation declares («…es para 40 viajeros» / «…2 servicios independientes (entre 16 y 32 viajeros; el número real lo confirma el personal al convertir)») **and** «Aquí puedes dejar hasta 30 pasajeros adicionales; el personal de D'spacios completa el resto al convertir la cotización». The header says «Hasta 30 además del titular».
* **At the limit** the panel says «Llegaste al máximo de 30 pasajeros adicionales … esto NO significa que ya estén todos los viajeros» — never «Ya están todos». Only when the universe itself ends at or below the limit (e.g. an exact universe of 31 = 30 additional) does it still say everyone is present.
* **Same number in all three layers**: panel (`capacidadCaptura`), action (`pasajeros.length > LIMITE_CAPTURA_ADICIONALES` → `mensajeLimiteCaptura()`, previously a literal `30` with the generic «lista no válida»), and the 326 function (`v_limite constant integer := 30`; a list over it raises `F4721` with the same sentence instead of letting the CHECK fire). Migration 326 is still **unapplied anywhere real**, so it was amended in place (preflight/postcheck updated: postcheck now has 7 controls, one for the limit; rollback unchanged — it restores the 325 definition).
* **Staff completion route preserved**: the staff conversion screens do not use the technical limit — they receive the ally's 30 and let staff add the missing rows up to the universe bound (journey ZR.5: 31 rows received, one more addable, button gone at 32).
