## 1. #62 — verification by code before the B2B approval request

### Decision implemented
Unverified users may log in (no login policy was changed: B2B accounts are inactive until approved, existing users stay verified). **A B2B approval request can only be created after the email is verified with a one-time code.** The authority is Supabase Auth (`email_confirmed_at`), re-read server-side after the code is accepted; nothing the browser sends can create the request.

### Flow
1. `iniciarRegistroB2B` (step 1): validations as before → creates the Auth user with `email_confirm: false`, server-only `app_metadata { registro_b2b_codigo: true, intentos_codigo: 0 }`, profile forced inactive (fail-closed as before) → `auth.resend({ type: "signup" })` sends the code. **No `b2b_solicitudes` row yet.** An abandoned earlier attempt of the same email (unverified, inactive, no request, server marker) is replaced; any other account with that email is untouched.
2. `confirmarCodigoYSolicitarB2B` (step 2): the pending registration is read from the server; `verifyOtp({ type: "signup" })`; then `getUserById` must show `email_confirmed_at` (else refused); only then the `b2b_solicitudes` row is inserted (type and name taken from the account created in step 1, not from the browser). Insert failure deletes the unverified account (can retry).
3. `reenviarCodigoB2B`: resend; neutral `ok` for unknown or non-pending emails; Auth's rate limit is surfaced as "Espera un momento…".
- **Bounded attempts:** 5 wrong codes (counter in `app_metadata`, server-written) delete the unverified registration; a new code requires registering again. The counter is read-modify-write (documented `shortcut:`): parallel guesses may under-count; the real burst limit is Auth's verification rate limit.
- **No new enumeration:** step 2 answers identically for unknown, old, approved or non-pending accounts and never calls Auth for them. Step 1 keeps the **pre-existing** "Ya existe una cuenta con ese correo" message (not changed, to preserve audited behaviour).
- **Forgery:** the marker lives in `app_metadata` (server-only). A marker forged in `user_metadata` (the only thing a user can write) never makes an account replaceable (tested).
- **UI** (`RegistroForm.tsx`): step 2 screen with a numeric code field, "Verificar y enviar solicitud", "Reenviar código" disabled for 60 s by a **local** 1 s timer (no requests; cleared on unmount); success ("Solicitud enviada") appears only when the server confirms. The password is not sent again in step 2.
- No migration (321 not used).

### Owner-side hosted configuration (cannot be tested locally by code)
1. Supabase Auth → "Confirm email" must be ON for the project (the resend/verify path relies on it).
2. Email template "Confirm signup" must contain the code: `{{ .Token }}` (local equivalent: `supabase/scripts/real_62/plantilla_confirmacion_codigo.html`).
3. Email OTP expiry (recommended 900 s = 15 min) and OTP length (6 recommended); the code accepts 6–10 digits.
4. Working outbound SMTP and acceptable email rate limits (the hosted defaults are low); the 60 s resend frequency is also an Auth setting.
5. `/portal/registro` needs no redirect URL (code is typed, no link).

## 2. #78 — "Solicitar contrato" separate from saving the quotation

### Decision implemented
An explicit **"Solicitar contrato"** button on each *vigente* quotation of the ally portal (`/portal/b2b/cotizaciones`). It persists a server-side event and creates **in-platform** notices (bell/avisos) for the configured responsible staff. No email, WhatsApp, SMS or webhook is sent (the checkout's existing manual WhatsApp/mailto hand-off is unchanged and out of scope; "Guardar/Generar cotización" still only saves).

### Migration 323 `20260601000323_solicitud_contrato_aviso.sql` (not run anywhere)
- Table `cotizacion_solicitudes_contrato` (RLS on, no policies, service_role only): at most ONE open event per quotation (partial unique index); a re-request with the quotation **unchanged** is idempotent; a re-request **after a change** (price, currency, dates, pax, state, B2B total) marks the previous event `reemplazada` and opens a new one.
- `avisos`: `tipo` CHECK extended with `solicitud_contrato`; new `cotizacion_id`.
- RPC `solicitar_contrato_cotizacion(p_cotizacion_id, p_actor)` (SECURITY DEFINER, `search_path=''`, service_role only) re-verifies under a row lock: active ally role, **ownership** (session email as `creado_por`, or the ally ficha frozen in `payload.b2bAsistido.aliado_id`), not converted, not discarded/comparative, not expired, departure not past. "Not yours" answers like "not found".
- **Recipients:** active internal users with role superadmin/gerencia/administracion/operaciones, of the quotation's agency (superadmin: any), whose email appears in the **existing** `config_solicitudes.emails`. No recipient is invented; with none configured the event is still saved (`notificados = 0`) and the ally sees an honest message.
- Scripts: `preflight_323…`, `postcheck_323…`, `rollback_323…` (one integral read-only query each; rollback refuses if events/notices exist), `test_323_solicitud_contrato.sql` (17 assertions on the real RPC).
