# Hostinger inbound adapter (#103) — code only, live behaviour OFF

Status 2026-11-22: **implemented and tested with simulated HTTP and a disposable database only.** No mailbox was connected, no credential was read or requested, no webhook was registered, no DNS/MX/billing/provider setting was touched, no e-mail was sent. It does nothing unless `SOLICITUD_PROVEEDOR_HOSTINGER=activo` and every setting below exists. Outbound mail is unchanged (Resend, or local capture). **Migration 330 is new and applied only on disposable databases** (next free number: 331). Because it is unapplied outside disposable copies it was amended IN PLACE for HIN-2a/2b (a column and a function argument) instead of adding a 331; if the owner had already applied the earlier version, a new numbered migration would be required (the repository's immutability rule).

## 1. Verified API contract (official OpenAPI read on 2026-11-22)
Sources: `https://developers.hostinger.com/openapi/openapi.json` (Hostinger API: mailbox/webhook management), `https://api.mail.hostinger.com/openapi/openapi.json` and `https://docs.hostinger.com/emails/mail-api.md` / `agentic-mail.md` (Mail API: what is inside a mailbox). The two APIs have separate base URLs and tokens.

| Fact | Documented? |
| --- | --- |
| Webhook event type: only `message.received` | yes |
| Delivery: HTTPS `POST`, JSON, `Authorization: Bearer <secret>` (the one-time secret returned when the webhook is created) | yes (OpenAPI; the help page says «verify request signatures» but no signature header/scheme exists in either spec — the Bearer is the only documented mechanism) |
| Webhook **payload** schema, event id, mailbox/message reference, signature, retry/timeout policy | **no** (help page: failing webhooks are paused automatically; last 20 deliveries visible) |
| `GET /api/v1/mailboxes/{mailboxResourceId}/folders/{folder}/messages` (`page`, `perPage` ≤ 100, `sort` = `uid`/`date`/`size`, `-` prefix descending) | yes → `{data:[Message], pagination}` |
| `POST …/messages/search?page&perPage&sort` with a JSON filter; `uid` = «IMAP UID set: single UID, range (1:100), open range (100:*), or comma-separated list» | yes → `{data:[Message]}`. Read-only despite the verb. Semantics NOT exercised live (A10): the adapter verifies every answer |
| `GET …/messages/{uid}` → `{data: Message}`; `GET …/messages/{uid}/text` → `{data:{text,html}}` | yes |
| `Message`: `uid, path, date, flags, unseen, size, subject, from{name?,address}\|null, to[], cc[], bcc[], messageId, inReplyTo, attachments[]`. `messageId` = RFC 5322 `Message-ID` header (angle brackets); `inReplyTo` = RFC string | yes. **No `references`, no header list.** |
| Errors `{error, code, params}`; `429` on rate limit (no `Retry-After` documented for this API) | yes |
| Send: `POST …/send` → `204`, returns **no message id**; `inReplyTo` there is `{uid, folder}`, not a Message-ID string | yes (not used by this adapter) |
| Plus-addressing (`respuestas+TOKEN@domain`) accepted by a mailbox; the tag preserved in `To` | **no** — assumption A1 |

**RFC Message-ID ≠ Resend email id.** `solicitudes_proveedor.mensaje_id` holds the id the PROVIDER returned at send time (Resend API email id, set by the `envio` event). A mailbox reports RFC `Message-ID`/`In-Reply-To` headers. They are different identifiers and are never compared: events from this adapter carry `espacio: "rfc822"` and `procesarEvento` skips the `mensaje_id` lookup for them (test H3).

## 2. Design
* Two entries run the SAME bounded pass (`drenarBuzonHostinger`): the webhook `POST /api/solicitud-proveedor/hostinger` and the scheduled drain `GET /api/cron/respuestas-hostinger`. Both routes are in `proxy.ts`' exact public lists (no session; the handlers are the gate) and share `hostingerDeps.ts` (database client, durable store, event processor, internal notice).
* **The notification is a trigger.** It is authenticated (constant-time Bearer comparison) and its body is **never parsed** — it cannot name a mailbox, folder or message (test H7). No Hostinger retry is assumed. The pass reads with the API token and **read-only calls** (GET and the documented search; never send/flag/move/delete) the configured mailbox's INBOX.
* Per message: (1) **correlation** = a Reply-To token in its `To`/`Cc` addresses, accepted only when the address is the configured reply address plus a tag (same local part and domain; ≤ 3 tokens). No token → ignored. (2) The token and the dedupe state are checked in the database **before** downloading: unknown token → ignored without any download; already recorded for that request → skipped. (3) Otherwise `GET message` (uid and Message-ID must equal the search entry) and `GET …/text`, then one `respuesta` event per matched request goes to the **existing** `procesarEvento` (state machine, dedupe RPC, contract identity via the request's own `contrato_uid`, tenant-scoped notices, internal e-mail only for a NEW event).
* Dedupe key: `hostinger:<mailbox id>:<RFC Message-ID>` (`uid:<uid>:<date>` if the header is absent; hashed if > 150 chars); the SQL unique key `(solicitud, tipo, dedupe)` stays the authority, so concurrent runs still store once and notify once.
* **A reply never confirms or rejects anything.** The only event produced is `respuesta` (state «respondida»); confirmation stays a person's `registrarDecision` (H10).

### 2.1 Durable continuation (Codex HIN-2) — migration 330
Two pieces of durable state, readable/writable only by the service role (RLS on, no policy, no grant to `anon`/`authenticated`; no tenant data, no reply content):
* **`hostinger_estado_buzon`** — per mailbox: `uid_cubierto` (every message with a uid up to it is handled), the sweep in progress (`barrido_tope`, `barrido_siguiente`), `barrido_desde` (the eligibility threshold of the sweep, see below; a CHECK forbids it without a running sweep) and a `version` for optimistic concurrency. `hostinger_estado_leer` creates/reads the row; `hostinger_estado_avanzar` moves it only if `version` is still the one the caller read (compare-and-swap).
* **`hostinger_respuestas_pendientes`** — replies found but not yet downloaded/recorded (uid + dedupe + attempts). They stay until recorded or the message no longer exists: **they never age out**, even beyond the 72 h discovery window.

A run: (0) reads the state; (1) retries the oldest parked replies first (`PENDIENTES_MAX = 10` per run); (2) resumes the sweep: if nothing newer than `uid_cubierto` exists it ends after ONE call; otherwise a sweep starts at the newest uid and scans **downward by uid range** (`POST …/messages/search`, body `{uid:"<cubierto+1>:<siguiente>"}`, newest first, `POR_PAGINA = 100`) page after page and ends **only when that uid range is exhausted** (a short page, or `uid_cubierto` reached) — never because of a date; the finished sweep sets `uid_cubierto = tope` and the run loops back to look for mail that arrived meanwhile; (3) one last retry, after a short wait, of the replies parked in this run.
* **Progress inside a page (HIN-2a).** The cursor is saved after every fully handled page AND, when the budget ends in the middle of a page, down to the first unhandled message of that page (`barrido_siguiente` = the highest unhandled uid; everything above it is recorded, skipped or parked). A long already-recorded prefix can therefore never consume every run's budget: the next run starts below it. The save uses the budget's reserved tail (below), goes through the same compare-and-swap, and never passes an unhandled reply (tests P1–P4).
* **Eligibility across days (HIN-2b).** Only the FIRST sweep of a mailbox (cursor 0) has an age limit (`VENTANA_HORAS = 72`, so years of old mail are not resurrected); its threshold is computed ONCE when the sweep starts and SAVED in `barrido_desde`, and every run that resumes that sweep — the next scheduled run a day or four days later — applies the same threshold. A reply that was eligible when the sweep began is therefore never dropped because time passed, and an unfinished region is never labelled covered (tests X1–X2). Age is only a per-message SKIP, **never a stop rule** (sender dates are not monotonic with uids; X3). The search carries **only the uid range — no `since` (HIN-4)**: the provider's `since` is arrival-based while the skip uses the sender `date`, and filtering on one timestamp cannot implement eligibility defined on the other (a reply with a recent sender date that arrived days ago, or the reverse, would be hidden by the filter, and the uid-range validation cannot detect a message a filter omitted). The cost is that the first sweep of a long mailbox pages through old mail (one search per 100 messages) and skips it locally (S8). Every LATER sweep has no age limit: everything above the cursor is unhandled and eligible however old its date or however long nobody ran (X4). A uid reset restarts as a first sweep with a fresh threshold (X5).
* **No page cap.** Depth per run is limited only by the budget below; the next run resumes at the saved position. A reply buried under any amount of newer unrelated mail is reached after enough runs — **without any new mail** (tests S1, S3, S4).
* **Newer or deleted mail between runs is harmless:** the position is a uid, so arrivals (higher uids) and deletions cannot shift it; the next sweep covers only uids above the previous top (S3, S4). If uids ever go backwards (mailbox recreated) the cursor resets and the sweep restarts safely (recorded replies are skipped) (S8).
* **Failed downloads:** parked in the backlog **before** the cursor moves past them (even when the run has no HTTP attempts left: database work is gated by time only) (S5, S5b); retried first by every later run; one brief blip is recovered inside the same run (S6).
* **Concurrent runs:** the cursor advances only through the compare-and-swap; of N simultaneous runs exactly one advances each step and the others stop at their first lost race (`conflicto`); their work is idempotent (the RPC's unique key stores each reply once and notifies once) (S7, S7b; real SQL: 8 concurrent sessions, exactly one winner).
* **Untrusted search:** every returned uid must lie inside the requested range; otherwise the pass fails loudly (502) and the cursor stays at the last trusted page (S9). An unreadable NEWEST entry is an error, never «empty mailbox».

### 2.2 One shared budget (Codex HIN-3)
One `Presupuesto` — a deadline (`PRESUPUESTO_MS = 8 s`, of which the last `RESERVA_GUARDADO_MS = 1 s` is RESERVED: item work stops at the soft end, and saving progress/parking/cursor writes may use the rest) and an HTTP-attempt allowance (`SOLICITUDES_MAX = 60`) — governs everything one pass does:
* **Inside every retry and wait:** the client checks the deadline and the allowance before each attempt and before each backoff wait; an attempt's timeout is `min(10 s, time left)`; a wait is clipped to what is left (minus a 250 ms margin) or the call ends with «presupuesto»; attempts are drawn from the shared allowance, so a three-attempt call can never cross it (B1, B2, B3).
* **Database, event and store work:** every call is raced against the deadline (`limitar`); a slow check/RPC/store write stops the pass (`presupuestoAgotado`, `completo:false`, webhook 202) with the cursor not advanced past unhandled mail; a call already in flight cannot be cancelled (it finishes idempotently or is bounded by its own timeout) and a rejection that arrives after the deadline is absorbed, not an unhandled rejection (B4, B5). A genuine database error still fails the pass (500) (B6).
* The 8 s sits deliberately below a 10 s default function limit; the real hosted limit is unknown (A9).

### 2.3 Honest status and who starts the next pass
`completo: true` only when the sweep reached the newest message with nothing newer than the cursor, no parked reply remains, nothing was left for lack of budget, and no conflict or inconsistency happened. Otherwise the summary says why and the webhook answers **202** (`pendiente: true`), never 200. Next passes are started by any later notification and by the **scheduled drain** `/api/cron/respuestas-hostinger` (daily entry in `vercel.json` — a sub-daily schedule would be rejected on a Hobby plan; an external scheduler may call it more often with the same `CRON_SECRET` bearer; answers 200 «desactivado» while the Hostinger entry is off). No self-calling loop exists. Responses: `503` disabled/incomplete configuration or rejected API token (nothing touched); `401` bad Bearer; `413`; `200` complete; **`202` incomplete**; `502` mailbox unreadable on the first call or search not honoured; `500` database failure. Bodies carry counts only, never message data.
HTTP client (injectable `fetch`/sleep): `INTENTOS_MAX = 3` attempts for 429/5xx/timeout/network (`Retry-After` honoured, capped at 5 s; otherwise 500 ms·2ⁿ); 401/403, 404 (message vanished: counted, not retried), other 4xx and non-JSON are not retried; bodies and the token are never echoed.

## 5. Remaining integration assumptions (none verified against a real mailbox)
* **A1** Hostinger accepts mail for `respuestas+TOKEN@domain` (plus-addressing, or a catch-all/alias that delivers it) and the received message keeps the tag in `To`/`Cc`. Not documented. If false, replies bounce or arrive without a token and are ignored (fail closed). Alternatives need an owner decision (unique alias per request is impractical; a token in the subject/body changes the outbound layout).
* **A2** The `message.received` webhook fires for that mail and its delivery is a POST with the Bearer. The payload is unknown and deliberately unused; the Test button/endpoint also triggers a (harmless) pass.
* **A3** Hostinger's retry and auto-pause rules are undocumented and NOT assumed. Recovery does not need them: the durable cursor/backlog and the scheduled drain finish whatever a lost, paused or failed notification left. Answering `502/503` for our own upstream failures could still contribute to an automatic pause; monitor «Recent deliveries» after enabling. How often the drain runs is an owner decision (daily in `vercel.json`; more often needs an external scheduler or a plan that allows it). **With only the daily drain, a pending reply can wait up to a day for its next attempt unless another notification arrives.**
* **A4** `INBOX` is the folder name and `sort=-uid`/`perPage` ≤ 100 are accepted (documented, not exercised). Reading a message might mark it `\Seen` (not stated).
* **A5** No `In-Reply-To` correlation: the Resend send API does not give us the outbound RFC `Message-ID`, and the Mail API exposes no `References`. Adding it needs (a) proof of how to obtain the outbound RFC id (e.g. Resend's retrieve-email data — unverified) and (b) a new column/migration (next free number 331). Until then the token is the only correlation; a reply that loses the tag is not linked.
* **A6** Any sender who knows the unguessable token can post a «reply» notice (same trust level as the existing Resend path); the sender address is recorded and shown, not enforced against the request's recipients (owner policy).
* **A7** Attachments and HTML bodies of replies are ignored; the text part is stored truncated to 2,000 characters.
* **A8** The Mail API rate limit values and the API token's permission model were read, not exercised. A sweep of a very large mailbox makes many search calls over successive runs (≈ 58 per run); rate limiting or request cost at that volume is unmeasured.
* **A9** The hosted function duration limit is unknown; `PRESUPUESTO_MS = 8 s` and `SOLICITUDES_MAX = 60` are conservative local constants, not measured hosted values.
* **A10** The `POST …/messages/search` `uid` range and the `-uid` ordering behave as documented. The adapter does not trust them: any uid outside the requested range fails the pass. If Hostinger honoured the range but returned another order, correctness would still hold (the cursor uses the minimum uid of the page) but a page could be revisited.
* **A11** Cursor semantics assume IMAP uids grow with arrival within one mailbox lifetime; a backwards jump resets the sweep (costing one re-scan of the window).
* **A12 (revised, HIN-4)** The adapter does NOT use the provider's `since`. Eligibility of the first sweep is decided only locally: sender `date` against the saved threshold. If the sender date is much older than the arrival time (a very delayed or clock-skewed reply), the first-sweep skip may drop it; this residual rule is a product decision for the owner to accept (later sweeps have no age limit). The first sweep of a mailbox with a long history costs one search per 100 messages. If a matching arrival-time contract is ever established and tested, an arrival-based filter could be reintroduced as a separate, explicit change.

### Harness hardening (HJ-1 / HJ-2)

* **Reproducible (HJ-1).** The scratchpad-bound launcher and the missing stack/seed helpers were replaced by a sanitized harness in the repository (`harness.mjs`, `lib.mjs`, `gateway.mjs`, `auth_owner_fix.sql`): checkout-relative paths, explicit settings (`HJ_WORK`, `HJ_PG_CONTAINER`, `HJ_TEMPLATE_DB`, `HJ_DB`, `HJ_APP_PORT`), credentials and journey secrets generated per work folder outside the repository (`init` refuses a work folder inside it), one documented sequence. The journey restarts the app through the harness, not through an external script.
* **Disposable target validated before every destructive statement (HJ-1).** The target database must match `hj103_[a-z0-9_]+` AND carry a marker comment written only when the harness itself created it; otherwise `up`/`seed`/`down` and the journey's own SQL runner refuse before any statement. Containers and the network are removed only if they carry the harness label.
* **No kill-by-port, loopback bind (HJ-2).** `next start` is launched with `-H 127.0.0.1` (Next's default is all interfaces) and the launcher then proves it: every listener address is 127.0.0.1 and every non-loopback address of the machine refuses a connection. An occupied port makes start **refuse** (the foreign process is never touched). Stop acts only on a process recorded by the launcher whose pid, start time and command line still match (protection against PID reuse); otherwise it refuses.
* **Evidence (`checks_harness.mjs`, focused, no journey).** See the results in the delivery report §0.H5.

### Dedicated PostgreSQL container (HJ-3)

The earlier `up` ran `ALTER ROLE authenticator …; ALTER ROLE supabase_auth_admin …` and terminated template sessions in whatever container `HJ_PG_CONTAINER` named; a database marker does not protect other databases of that cluster. The harness now mutates **only** a dedicated container it creates itself (`hj103_pg`, `pg-create`; no published port). A single guard (`exigirContenedorPropio`) runs before any template/database/role statement — every SQL call goes through it, and `up` calls it first, before ports, teardown or database creation: fixed name, full container id equal to the ownership record written at creation (a pre-existing container cannot acquire it; relabelling is useless), harness labels, running, and no non-harness database in the cluster. An explicit `HJ_PG_CONTAINER` other than `hj103_pg` is only ever refused. The base schema reaches the dedicated container by a **read-only** `pg_dump` of a source container/template (`HJ_SOURCE_*`). A deliberately forged record on an *empty* cluster is an explicit adoption by the person who writes it; a forged record on a cluster with foreign databases is still refused. Evidence: `checks_pg_ownership.mjs` (delivery report §0.H6).
